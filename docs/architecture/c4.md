# C4 architecture views

[Architecture guide](README.md) · [Progressive explanation](overview.md) · [Accepted architecture](../plans/accepted/domain-architecture.md)

This page illustrates the system context (Level 1), browser applications and stores (Level 2), and internal component boundaries (Level 3) of Granaderos using the C4 model. It connects the high-level [overview](overview.md) to the repository directories in the [system map](system-map.md) and the sequence traces in [runtime flows](runtime-flows.md).

The runnable applications are `apps/web` and `apps/campaign-editor`; the reusable packages are `packages/game` and `packages/campaign-format`. Each application bundles the code it imports into a static browser deployment. See the [repository map](../development/repository-layout.md) for directory navigation.

The diagrams follow the official C4 scopes: a [system context](https://c4model.com/diagrams/system-context) shows people and external systems; a [container view](https://c4model.com/diagrams/container) shows independently built browser applications, workers, and data stores; and a [component view](https://c4model.com/diagrams/component) shows internal responsibilities inside each application. In C4 terminology, a container is a runtime execution or storage boundary, not a Docker image or server process.

## Level 1: people and the system

The diagram below shows how the `Player`, `Campaign author`, and `Publisher` interact with `Granaderos` and how `Static hosting` distributes the built files and campaign packages.

```mermaid
flowchart TB
  Player["Player<br/>Person<br/>Directs a force and its combatants"]
  Author["Campaign author<br/>Person<br/>Creates worlds, characters, and objectives"]
  Publisher["Publisher<br/>Person<br/>Builds and distributes campaign packages"]
  Granaderos["Granaderos<br/>Software system<br/>Plays campaigns and creates campaign projects"]
  Hosting["Static hosting<br/>External software system<br/>Distributes the application and campaign resources"]
  Player -->|Plays campaigns and imports or exports progress| Granaderos
  Author -->|Edits, validates, and tests campaign projects| Granaderos
  Publisher -->|Builds and checks distribution files| Granaderos
  Granaderos -->|Produces distribution files for publication| Hosting
  Hosting -->|Delivers the game, editor, and campaign resources| Granaderos
```

The `Player` issues strategic and sector orders in the browser and exports or imports save files. The `Campaign author` creates, validates, and playtests campaign drafts without writing arbitrary executable scripts. The `Publisher` runs the build pipeline to stage static files for `Static hosting`, which serves `Granaderos` over HTTP without a backend gameplay server.

## Level 2: applications and storage

The diagram below shows how the `Player` and `Campaign author` use the `Game application` and `Campaign editor application` inside `Granaderos`, and how those applications exchange data with `Static distribution`, `Game worker processes`, `Game save store`, `Project store`, and `User files`.

```mermaid
flowchart TB
  Player["Player<br/>Person"]
  Author["Campaign author<br/>Person"]
  Host["Static distribution<br/>HTTP files<br/>Game, editor, campaign JSON, and media"]
  subgraph System[Granaderos]
    Game["Game application<br/>React and TypeScript/JavaScript<br/>Campaign and sector play"]
    Editor["Campaign editor application<br/>React and Vite<br/>Project editing, validation, and isolated playtests"]
    Workers["Game worker processes<br/>Web Workers<br/>Tactical calculation, save encoding, and visual fitting"]
    Saves[("Game save store<br/>Browser localStorage<br/>Portable game snapshot per campaign key")]
    Projects[("Project store<br/>Browser IndexedDB<br/>Draft documents and resource bytes")]
  end
  Files[("User files<br/>Downloaded or selected files<br/>Saves, project archives, and campaign packages")]
  Player -->|Browser controls| Game
  Author -->|Browser controls| Editor
  Host -->|HTTP GET: application and resources| Game
  Host -->|HTTP GET: application and resources| Editor
  Game <-->|Structured-cloned jobs and results| Workers
  Game -->|Web Lock ownership and localStorage API| Saves
  Saves -->|Read saved JSON| Game
  Editor <-->|IndexedDB transactions| Projects
  Game <-->|Browser file selection and download| Files
  Editor <-->|Browser file selection and download| Files
```

`Game application` (`apps/web`) and `Campaign editor application` (`apps/campaign-editor`) have separate entry points and build outputs. The game routes `/studio`, `/story`, and `/editor` link to the editor application at `/campaign-editor/`. Editor playtests and previews run through `packages/game/public` and `apps/web/game-preview.ts` inside an isolated session in `Editor` rather than mutating the `Game save store` (`localStorage`) of an open game tab. `Editor` persists mutable drafts and binary resources in `Project store` (`IndexedDB`), while both applications import and export portable files through `User files`.

Both applications bundle [`packages/campaign-format`](../../packages/campaign-format/README.md) as a shared library for published schemas, identifiers, resource hashes, and immutable `CampaignDefinition` objects. `Game application` (`apps/web`) spawns `Game worker processes` (Web Workers) for tactical step calculation, save encoding, and 3D contact fitting; workers return data to their caller and never write directly to `Saves` or `Projects`.

Source entry points: [`apps/web/app/page.tsx`](../../apps/web/app/page.tsx), [`apps/campaign-editor/web/main.tsx`](../../apps/campaign-editor/web/main.tsx), [`apps/campaign-editor/vite.config.mjs`](../../apps/campaign-editor/vite.config.mjs), [`tools/build-web.mjs`](../../tools/build-web.mjs), [`apps/web/lib/useBattleExecutor.ts`](../../apps/web/lib/useBattleExecutor.ts), [`apps/web/lib/browser-save-writer.ts`](../../apps/web/lib/browser-save-writer.ts), and [`apps/campaign-editor/web/lib/campaign-studio-storage.ts`](../../apps/campaign-editor/web/lib/campaign-studio-storage.ts).

## Level 3: game application components

The diagram below shows the components inside the `Game application` and how `Game UI and composition` coordinates `Application use cases`, `Use-case repository contracts`, `Repository adapters`, `Domain model`, `GameUnitOfWork and identity map`, `GameSnapshotMapper and save codec`, `Compatibility rule engine`, `Browser persistence adapter`, `Observation and rendering adapters`, `Worker process`, and `Browser save store`.

```mermaid
flowchart TB
  Input["Game UI and composition<br/>React screens, hooks, and input adapters"]
  subgraph Game[Game application]
    UseCases["Application use cases<br/>Recruit, resolve arrival, act in a sector,<br/>converse, query visibility, advance world, save, and restore"]
    Ports["Use-case repository contracts<br/>Narrow reads, commands, and commit interfaces"]
    Repositories["Repository adapters<br/>Load context and publish accepted changes"]
    Domain["Domain model<br/>Character, Health, CharacterAbilities, Squad,<br/>ServiceContract, and Treasury;<br/>Journey, SectorSession, CombatSession;<br/>Inventory, perception, and world lifecycles"]
    Transaction["GameUnitOfWork and identity map<br/>One accepted revision and shared identities"]
    Mapper["GameSnapshotMapper and save codec<br/>Restore behavior, validate relationships,<br/>project versioned snapshots"]
    Compatibility["Compatibility rule engine<br/>Campaign/tactical entry points, geometry,<br/>scenario rules, and wire-field adapters"]
    PersistenceAdapter["Browser persistence adapter<br/>Save queue, ownership lock, and storage status"]
    Presentation["Observation and rendering adapters<br/>HUD, Three.js, animation, and sound"]
  end
  Worker["Worker process<br/>Calculation or encoding"]
  Storage[("Browser save store")]
  Input -->|Executes an intention| UseCases
  Input -->|Dispatches compatibility orders| Compatibility
  Compatibility -->|Routes migrated intentions| UseCases
  UseCases -->|Runs behavior| Domain
  UseCases -->|Reads and commits through| Ports
  Repositories -.->|Implements| Ports
  Repositories -->|Restores and applies| Domain
  Repositories -->|Shares atomic work and identities| Transaction
  Repositories -->|Converts accepted state| Mapper
  Repositories -->|Calls rules still in compatibility modules| Compatibility
  Input -->|Submits jobs and admits current results| Worker
  Worker -->|Runs shared rule entry points| Compatibility
  Input -->|Provides accepted observations| Presentation
  PersistenceAdapter -->|Executes SaveGame| UseCases
  PersistenceAdapter -->|Encodes and restores| Mapper
  PersistenceAdapter -->|Writes under its save lock| Storage
```

Each use case in `Application use cases` (`packages/game/application`) owns one narrow interface in `Use-case repository contracts`. `Repository adapters` (`packages/game/infrastructure`) implement those interfaces and share `GameUnitOfWork and identity map` and `GameSnapshotMapper and save codec` so all objects in a transaction reference one canonical owner for `Character`, `Health`, `Inventory`, `ItemCustody`, `Squad`, `Journey`, and `SectorSession`. `Compatibility rule engine` (`packages/game/campaign.js`, `packages/game/tactical.js`, and root rule modules) routes migrated intentions to `Application use cases` and executes procedural rules that have not yet moved into `Domain model`.

## Level 3: campaign editor components

The diagram below shows how the `Campaign author` interacts with the components inside the `Campaign editor application` (`Editor workspaces`, project and map editing use cases, `CampaignWorld and CampaignMap`, `SectorMap and SectorMapHistory`, `ValidateCampaignProject`, `CampaignProject and CampaignProjectHistory`, `Project repositories and browser adapters`, `campaign-format library`, `Public game integration`, and `Public preview UI contract`) and the `Browser project store`.

```mermaid
flowchart TB
  Author["Campaign author<br/>Person"]
  subgraph Editor[Campaign editor application]
    UI["Editor workspaces<br/>Project, world, maps, cast, presentation, and resources"]
    Edit["EditCampaignProject, UndoCampaignProjectEdit,<br/>and RedoCampaignProjectEdit<br/>Expected revision, admission, and history"]
    MapEdit["EditSectorMap<br/>Ordered edit batch and atomic map commit"]
    Policies["CampaignWorld and CampaignMap<br/>Locality membership, links, references,<br/>campaign map admission, and slabs"]
    SectorMap["SectorMap and SectorMapHistory<br/>Building, terrain, object, and template edits;<br/>bounded undo/redo"]
    Validate["ValidateCampaignProject<br/>Read-only validation report"]
    Project["CampaignProject and CampaignProjectHistory<br/>Identity, draft envelope, resource mutations, and undo/redo"]
    Repositories["Project repositories and browser adapters<br/>Revision checks, IndexedDB, files, and archives"]
    Format["campaign-format library<br/>Published content, world, map, and presentation schemas<br/>References and immutable CampaignDefinition"]
    GameAPI["Public game integration<br/>Validation, rule choices, map preview, and isolated playtest"]
    Preview["Public preview UI contract<br/>Battlefield renderer, presentation, and draft asset resolution"]
  end
  ProjectStore[("Browser project store")]
  Author -->|Edits and tests a project| UI
  UI -->|Submits studio draft edits| Edit
  UI -->|Submits map command batches| MapEdit
  UI -->|Prepares a coordinated world or map edit| Policies
  MapEdit -->|Runs authoring behavior| SectorMap
  MapEdit -->|Loads and commits| Repositories
  SectorMap -->|Uses injected geometry and validation port| GameAPI
  UI -->|Requests report| Validate
  Edit -->|Uses project behavior| Project
  Edit -->|Loads and commits| Repositories
  Validate -->|Reads draft| Repositories
  Validate -->|Calls the read-only validation port| GameAPI
  Project -->|Checks published structure| Format
  Repositories <-->|Stores draft documents and bytes| ProjectStore
  Repositories -->|Imports and exports package files| Format
  UI -->|Runs a separate game session| GameAPI
  UI -->|Presents previews| Preview
```

`CampaignProject` and `CampaignProjectHistory` own mutable project drafts, binary resource catalogs, and undo/redo snapshots. `EditCampaignProject`, `UndoCampaignProjectEdit`, and `RedoCampaignProjectEdit` mutate project state through `Project repositories and browser adapters` at an expected revision and persist drafts in `Browser project store` (`IndexedDB`). `CampaignWorld` owns strategic locality and route invariants; `CampaignMap` owns the fixed 20x16 campaign map slot; and `SectorMap` with `SectorMapHistory` owns physical map authoring batches submitted through `EditSectorMap`.

`ValidateCampaignProject` inspects the draft without mutating it, combining `campaign-format library` (`CampaignDefinition` and `CampaignContentSchema`) with `Public game integration` (`packages/game/public/campaign-editor-api.ts`). `Public game integration` (`packages/game/public/campaign-playtest-api.ts`) and `Public preview UI contract` (`apps/web/game-preview.ts` and `apps/web/game-preview-assets.js`) run isolated map previews and campaign sandboxes without importing internal game modules or touching player saves.

## How to check a boundary claim

Two automated checks enforce the import and layer rules shown above:

- `npm run check:architecture` (backed by [`tools/check-architecture.mjs`](../../tools/check-architecture.mjs)) verifies that `packages/game` never imports `apps/campaign-editor`, `domain` code imports only `domain` code (plus `packages/campaign-format` in the editor domain), `application` code imports only `application` and `domain` contracts, `apps/campaign-editor` reaches `packages/game` and `apps/web` only through their declared public entries, and `domain` and `application` files never call browser globals or ambient `Math.random`.
- `npm run check:dependencies` evaluates the rules in [`.dependency-cruiser.json`](../../.dependency-cruiser.json), enforcing the same layer boundaries, forbidding production imports from `tools/` or test files, and rejecting runtime circular dependencies within `domain` and `application`.

For the full build and verification pipeline, continue to [build and tooling](build-and-tooling.md).
