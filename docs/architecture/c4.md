# C4 architecture views

[Architecture guide](README.md) · [Progressive explanation](overview.md) · [Accepted architecture](../plans/accepted/domain-architecture.md)

These diagrams describe the browser implementation in the working source on
28 October 2026. They separate software users, running applications, data stores,
and components. The `game`, `campaign-editor`, and `campaign-format` packages are
source boundaries. The applications are `apps/web` and `apps/campaign-editor`;
the reusable packages are `packages/game` and `packages/campaign-format`.
Each application bundles the code it uses. See the
[repository map](../development/repository-layout.md) for source navigation.

The views follow the official C4 scopes: a [system context](https://c4model.com/diagrams/system-context)
shows people and systems; a [container view](https://c4model.com/diagrams/container)
shows applications and data stores; a [component view](https://c4model.com/diagrams/component)
shows responsibilities inside one application. A C4 container does not imply
Docker or a server process.

## Level 1: people and the system

```mermaid
flowchart LR
  Player["Player<br/>Person<br/>Directs a force and its combatants"]
  Author["Campaign author<br/>Person<br/>Creates worlds, characters and objectives"]
  Publisher["Publisher<br/>Person<br/>Builds and distributes campaign packages"]
  Granaderos["Granaderos<br/>Software system<br/>Plays campaigns and creates campaign projects"]
  Hosting["Static hosting<br/>External software system<br/>Distributes the application and campaign resources"]
  Player -->|Plays campaigns and imports or exports progress| Granaderos
  Author -->|Edits, validates and tests campaign projects| Granaderos
  Publisher -->|Builds verified distribution files| Granaderos
  Granaderos -->|Produces distribution files for publication| Hosting
  Hosting -->|Delivers the game, editor and campaign resources| Granaderos
```

The player chooses orders. The simulation determines their consequences. The
campaign author supplies supported data. Authored data does not install arbitrary
executable rules. The exported game runs in the browser without a gameplay server.

## Level 2: applications and storage

```mermaid
flowchart TB
  Player["Player<br/>Person"]
  Author["Campaign author<br/>Person"]
  Host["Static distribution<br/>HTTP files<br/>Game, editor, campaign JSON and media"]
  subgraph System[Granaderos]
    Game["Game application<br/>React and TypeScript/JavaScript<br/>Campaign and sector play"]
    Editor["Campaign editor application<br/>React and Vite<br/>Project editing, validation and isolated playtests"]
    Workers["Game worker processes<br/>Web Workers<br/>Tactical calculation, save encoding and visual fitting"]
    Saves[("Game save store<br/>Browser localStorage<br/>Portable game snapshot per campaign key")]
    Projects[("Project store<br/>Browser IndexedDB<br/>Draft documents and resource bytes")]
  end
  Files[("User files<br/>Downloaded or selected files<br/>Saves, project archives and campaign packages")]
  Player -->|Browser controls| Game
  Author -->|Browser controls| Editor
  Host -->|HTTP GET: application and resources| Game
  Host -->|HTTP GET: application and resources| Editor
  Game <-->|Structured-cloned jobs and results| Workers
  Editor <-->|Playtest and preview jobs and results| Workers
  Game -->|Web Lock ownership and localStorage API| Saves
  Saves -->|Read saved JSON| Game
  Editor <-->|IndexedDB transactions| Projects
  Game <-->|Browser file selection and download| Files
  Editor <-->|Browser file selection and download| Files
```

The two applications have separate entry points and builds. The game routes
`/studio`, `/story`, and `/editor` contain links to the editor application at
`/campaign-editor/`. Editor playtests execute the game's public API inside an
isolated session in the editor application. They do not send commands to the
player's open game tab.

The shared [`campaign-format`](../../packages/campaign-format/README.md) package is a code
library used by both applications. It defines published campaign contracts,
identifiers, file schemas, cross-reference checks, resource hashes, and immutable definitions. It is not a
separate runtime service. The [`game`](../../packages/game/package.json) package supplies
rules and public integration APIs. Its runtime imports no editor implementation.

Each browser application creates its own workers as needed. Workers return data
to their caller. The save worker cannot write localStorage. The browser save
adapter holds one exclusive lock for each save key and reports accepted progress
separately from persisted progress.

## Level 3: game application components

```mermaid
flowchart TB
  Input["Game UI and composition<br/>React screens, hooks and input adapters"]
  subgraph Game[Game application]
    UseCases["Application use cases<br/>Recruit, resolve arrival, act in a sector,<br/>converse, query visibility, advance world, save and restore"]
    Ports["Use-case repository contracts<br/>Narrow reads, commands and commit interfaces"]
    Repositories["Repository adapters<br/>Load context and publish accepted changes"]
    Domain["Domain model<br/>Character, Health, CharacterAbilities, Squad,<br/>ServiceContract and Treasury;<br/>Journey, SectorSession, CombatSession;<br/>Inventory, perception and world lifecycles"]
    Transaction["GameUnitOfWork and identity map<br/>One accepted revision and shared identities"]
    Mapper["GameSnapshotMapper and save codec<br/>Restore behavior, validate relationships,<br/>project versioned snapshots"]
    Compatibility["Compatibility rule engine<br/>Campaign/tactical entry points, geometry,<br/>scenario rules and wire-field adapters"]
    PersistenceAdapter["Browser persistence adapter<br/>Save queue, ownership lock and storage status"]
    Presentation["Observation and rendering adapters<br/>HUD, Three.js, animation and sound"]
  end
  Worker["Worker process<br/>Calculation or encoding"]
  Storage[("Browser save store")]
  Input -->|Executes an intention| UseCases
  Input -->|Dispatches compatibility orders| Compatibility
  Compatibility -->|Routes migrated intentions| UseCases
  UseCases -->|Runs behavior| Domain
  UseCases -->|Reads and commits through| Ports
  Repositories -.->|Implements| Ports
  Repositories -->|Restores and applies| Domain
  Repositories -->|Shares atomic work and identities| Transaction
  Repositories -->|Converts accepted state| Mapper
  Repositories -->|Calls rules still in compatibility modules| Compatibility
  Input -->|Submits jobs and admits current results| Worker
  Worker -->|Runs shared rule entry points| Compatibility
  Input -->|Provides accepted observations| Presentation
  PersistenceAdapter -->|Executes SaveGame| UseCases
  PersistenceAdapter -->|Encodes and restores| Mapper
  PersistenceAdapter -->|Writes under its save lock| Storage
```

The repository interface belongs to its use case. Adapters share transaction,
identity, mapping, and storage mechanisms. The domain and application directories
do not depend on React or browser APIs. Public application entry modules are
composition adapters in `packages/game/public` and `apps/campaign-editor/public`. They can
construct concrete infrastructure for callers. Application modules have no
exception to the rule that they import only their own contracts and domain.

The compatibility component is material. `campaign.js`, `tactical.js`, and many
specialized rule modules still execute gameplay rules. Their names and save fields
are mapped explicitly where a migrated domain slice uses canonical terms. The
presence of a domain class does not establish that every rule of that subsystem
has moved into it.

## Level 3: campaign editor components

```mermaid
flowchart TB
  Author["Campaign author<br/>Person"]
  subgraph Editor[Campaign editor application]
    UI["Editor workspaces<br/>Project, world, maps, cast, presentation and resources"]
    Edit["EditCampaignProject, UndoCampaignProjectEdit<br/>and RedoCampaignProjectEdit<br/>Expected revision, admission and history"]
    MapEdit["EditSectorMap<br/>Ordered edit batch and atomic map commit"]
    Policies["CampaignWorld and CampaignMap<br/>Locality membership, links, references,<br/>campaign map admission and slabs"]
    SectorMap["SectorMap and SectorMapHistory<br/>Building, terrain, object and template edits;<br/>bounded undo/redo"]
    Validate["ValidateCampaignProject<br/>Read-only validation report"]
    Project["CampaignProject and CampaignProjectHistory<br/>Identity, draft envelope, resource mutations and undo/redo"]
    Repositories["Project repositories and browser adapters<br/>Revision checks, IndexedDB, files and archives"]
    Format["campaign-format library<br/>Published content, world, map and presentation schemas<br/>References and immutable CampaignDefinition"]
    GameAPI["Public game integration<br/>Validation, rule choices, map preview and isolated playtest"]
    Preview["Public preview UI contract<br/>Battlefield renderer, presentation and draft asset resolution"]
  end
  ProjectStore[("Browser project store")]
  Author -->|Edits and tests a project| UI
  UI -->|Submits every studio draft edit| Edit
  UI -->|Submits map command batches| MapEdit
  UI -->|Prepares a coordinated world or map edit| Policies
  MapEdit -->|Runs authoring behavior| SectorMap
  MapEdit -->|Loads and commits| Repositories
  SectorMap -->|Uses injected geometry and validation port| GameAPI
  UI -->|Requests report| Validate
  Edit -->|Uses project behavior| Project
  Edit -->|Loads and commits| Repositories
  Validate -->|Reads draft| Repositories
  Validate -->|Calls the read-only validation port| GameAPI
  Project -->|Checks published structure| Format
  Repositories <-->|Stores draft documents and bytes| ProjectStore
  Repositories -->|Imports and exports package files| Format
  UI -->|Runs a separate game session| GameAPI
  UI -->|Presents previews| Preview
```

`CampaignDefinition` checks the complete published file set through neutral
schemas. `CampaignContentSchema` admits characters, equipment, dialogue, quests,
placements and configured rules. World and map schemas admit their records and
references. Presentation and physical-source schemas check their own documents.
The public game API adds supported capabilities, compiled map geometry and access,
concrete item behavior, escort feasibility and scenario compatibility. File
validation creates no mutable game progress.

Editor projects can remain incomplete. Validation controls playable packages and
installable export. Undo history stores owned snapshots. Browser resources and
object URLs remain outside published definitions.

The campaign studio sends draft changes, renames and history actions through
application use cases. Its editing repository owns one project history and checks
the expected revision. Opening another project invalidates pending callbacks.
Validation reads that same model and returns the inspected revision.

`CampaignWorld` owns linked locality, district, place and route changes, including
deletion-reference guards. `CampaignMap` owns the fixed campaign map slot and
slab access policy. The standalone and embedded sector editors use
`EditSectorMap`; `SectorMap` owns authoring transformations and transactional
command batches. The injected game API supplies shared geometry compilation and
schema validation. Renderer review scenes consume generated map documents;
the running game imports no map editing implementation.

## How to verify a boundary claim

Run `npm run check:architecture` for source import restrictions. Run
`npm --prefix apps/campaign-editor run build` for the independent editor artifact.
Use domain and application tests to verify invariants and refusal behavior. Use
browser checks for visible routes, controls, rendering, and file workflows.
These diagrams describe implementation structure; they do not certify completion
of a campaign or correctness of every retained rule.
